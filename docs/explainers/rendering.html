How a trillion particles become a picture

The picture above is a tiny version of the whole plan, running in your browser. No particle is saved anywhere. Each frame, every particle's position is worked out from its id number and the clock, pushed through a camera, and counted into a pixel. Then the counts are turned into brightness.

This guide walks through that chain one idea at a time, with the math, the computer science and the bit of physics behind each step. Most figures are live: drag the sliders.

Where the code stands today: main has the shared contracts, the camera and the behaviour building blocks. The renderer itself (src/render, src/challenge, src/offline, src/perf) is still being built in other threads. So the numbers here come from arithmetic, and the speed figures are estimates until the project measures them. Where a figure quotes project code, the file is named.

One particle's trip to a pixel

Follow a single particle through one frame of a 4K render. Every step is a small piece of arithmetic, and the GPU does the same steps for every other particle at the same time.

  1. Identityid = 7,301,442,118Particles are just the whole numbers 0, 1, 2 … up to the count. Nothing else exists about this particle yet.
  2. Randomnesshash(id, seed) → (0.613, 0.207)A hash scrambles the id into numbers between 0 and 1 that look random but come out the same every time. This is the particle's personal starting point.
  3. Plane spacemotion(start, t = 12.3 s) → (0.31, −0.58)The behaviour moves it to where it is at this moment. The sheet spans −1 to 1 on both axes, so this is "a bit right of centre, more than halfway down".
  4. World spacemodel × (0.31, −0.58, 0, 1) → (4.2, −1.1, 12.0)The plane's model matrix places the flat sheet in the 3D void: scale by its size, rotate, move.
  5. Clip spaceviewProj × world → (x, y, z, w)One more matrix moves the world so the camera sits at the origin and applies the lens. The fourth number, w, is the distance in front of the camera.
  6. Screen, −1 to 1(x / w, y / w) → (0.12, −0.33)Dividing by distance is what makes far things small. This is the perspective divide.
  7. Pixel(2150, 1436) of 3840 × 2160Stretch −1…1 to the image size and round down. Screen y points down, so y flips.
  8. Memory address1436 × 3840 + 2150 = 5,516,390The image is one long list of counters, row after row. This is the particle's slot.
  9. CountatomicAdd(counts[5516390], 1)Add one. The particle's whole contribution to the film is this single +1. Then it is forgotten.

In shader code the whole trip is about ten lines. This is a sketch of the idea, not the project's final shader:

// one invocation of this runs per particle, millions at a time
@compute @workgroup_size(256)
fn splat(@builtin(global_invocation_id) gid: vec3u) {
  let id   = globals.firstId + gid.x;               // which particle am I?
  let p    = motion(id, plane.seed, globals.time);  // plane space, never stored
  let clip = globals.viewProj * plane.model * vec4f(p, 0.0, 1.0);
  if (clip.w <= 0.0) { return; }                    // behind the camera
  let ndc  = clip.xy / clip.w;                      // perspective divide
  if (any(abs(ndc) >= vec2f(1.0))) { return; }      // off screen
  let px   = vec2u((ndc * vec2f(0.5, -0.5) + 0.5) * globals.size);
  atomicAdd(&counts[px.y * u32(globals.size.x) + px.x], 1u);
}

A detail that matters at this scale: a u32 id only reaches 4.29 billion. A trillion ids have to arrive in about 233 batches of 232, with the batch number mixed into the hash.

Perspective: divide by distance

A camera is a point (the eye) and a flat screen in front of it. To find where a particle lands, draw a straight line from the particle to the eye and mark where it crosses the screen. Similar triangles give the whole rule: the height on screen is the real height, times the screen distance, divided by how far away the particle is.

What this does to a sheet

A sheet of particles is flat. Turn it away from the camera and it covers fewer pixels, but it still holds the same number of particles. The same light is squeezed into a smaller area, so the sheet gets brighter as it turns edge-on. That is the reason a rotating camera in Strata keeps revealing new things: every angle re-sorts which particles share a pixel.

Motion without memory

The usual way to animate a particle is to store where it is, then nudge it forward a little each frame. That needs memory for every particle. The trillion-particle render uses a different idea: write the motion as a formula that answers "where is particle number id at time t?" directly.

The formula has two halves. A hash gives each id its own fixed random numbers (a starting spot, a speed, a lane). Then a closed-form motion moves that starting spot according to the clock. "Closed-form" means you can jump straight to any time without playing through the times before it.

Where structure comes from

If every particle started at a random spot and nothing else happened, the sheet would be flat grey fog. Patterns appear when the formula pushes many different starting spots toward the same places. In "folds", each point is pushed by a sine wave that depends on where it started. Neighbours get slightly different pushes, so in some places they are squeezed together and in others spread apart. Where they are squeezed, a bright crease appears, the same way light bunches into bright lines on the bottom of a swimming pool.

Curl noise: flow that never piles up

Smooth random noise is like a landscape of hills. Its slope (the gradient) points uphill. Turn every slope arrow a quarter turn and you get arrows that run along the hillsides, around the hills, like contour lines on a map. A flow like that never runs into a peak or out of a pit, so particles swirl forever without clumping or leaving holes. Mathematicians call it divergence-free. The project's curl2 block in src/behaviors/core/wgsl.ts does exactly this with three noise lookups.

Attractors: gravity with a safety valve

Real gravity pulls with a force of 1 / distance². That goes to infinity as the distance goes to zero, and a particle that passes very close gets flung away at absurd speed. Simulations fix this with softening: pretend the particle is never closer than a small distance s. The project's attract block uses force = r / (r² + s²)1.5.

The memory wall

In the stored (stateful) design, each particle is a position and a velocity on its sheet: four 32-bit numbers, 16 bytes (Particle in src/core/contracts.ts). Multiply by the particle count and compare with the memory on a graphics card.

Two ways to draw a dot

A GPU has a built-in drawing machine called the render pipeline. It was designed for triangles that cover many pixels each. You can ask it for one-pixel points, and for millions of particles that works well. But every point still pays for machinery it does not need. The alternative is to skip the machine and write the pixel yourself from a compute shader, which is a plain program that runs once per particle.

The built-in path stays the right tool for the realtime view. The frame graph in src/core/contracts.ts runs the stages simulate → interplane → rasterize → depth → tonemap → ui → capture, and "rasterize" there means additive points into a floating-point texture. The compute rasterizer is the special tool for the giant offline counts.

Counting safely when thousands write at once

A GPU runs thousands of particles at the same instant. With a trillion particles and eight million pixels, many of them want to add one to the same pixel at the same moment. Adding one is really three steps: read the number, add one, write it back. If two threads overlap, one of the additions vanishes.

How high can one pixel count?

The built-in blender adds light into a 16-bit floating-point texture (rgba16float, the project's hdrFormat). Floats keep about the same number of significant digits at every size, so big totals get coarse. A 16-bit float has only 11 bits of precision. Once a pixel's total reaches about 2,048 times the size of one particle's contribution, adding one more rounds back to the same number, and the pixel stops getting brighter. A plain 32-bit whole-number counter keeps counting exactly to 4.29 billion.

A pixel is a counter, an image is a histogram

A 4K frame has 8,294,400 pixels. A trillion particles is about 120,000 for every one of them. It is fair to ask what the point is, when most particles can never be seen as separate dots.

The answer is that the picture stops being a drawing of dots and becomes a measurement of density. Each pixel reports how many particles fell in it. With few particles that report is rough and grainy. With many, it becomes smooth and can tell apart very fine differences in brightness.

The square-root law

Particles land in a pixel at random, like raindrops in a bucket. Physics calls the resulting graininess shot noise, and it follows a simple rule: if a pixel expects n particles, the count typically wobbles by about √n. So the wobble relative to the signal is 1 / √n. Four times the particles gives half the grain. This is the same law that makes a long-exposure photo cleaner than a short one.

Tone mapping: from counts to brightness

The counter image can hold a pixel with 3 particles next to a pixel with 3 million. A screen can show 256 levels. Tone mapping is the rule that squeezes the first range into the second, and the choice of rule decides what the viewer can see.

linear
Brightness is the count divided by a chosen "white" count. Honest, but it can only show a range of about 256 to 1. Either the bright core clips to flat white or the faint parts vanish into black.
log
Brightness follows the logarithm of the count, so every ten-fold increase adds the same step of brightness. A range of a million to one fits on screen. This is close to how eyes judge brightness.
filmic
Nearly linear in the darks, then a smooth "shoulder" that eases toward white instead of clipping. The version here is extended Reinhard, the simplest curve of this family. It keeps contrast in the mid-tones and still holds detail in highlights.

A real pipeline has one more step after this curve: encoding for the display (sRGB gamma) and writing 8-bit video. That is left out here so the curves stay easy to compare. The project's RenderSettings.brightness plays the role of the white point: it scales counts before the curve.

Render time: the only limit left

With memory out of the way, a stateless render is limited by throughput: how many particles the GPU can compute and count per second. Everything follows from one division.

seconds per frame = particles ÷ particles per second
total time = seconds per frame × frames in the video

Two honest consequences. First, the trillion render is a patience problem, and every bit of work removed from the per-particle formula is hours saved. Second, because frames are independent, the render can stop and resume, or spread across several GPUs, without any change to the picture.

Words used here

splat
To deposit a particle's light into the pixel it lands on.
compute shader
A small program the GPU runs thousands of copies of at once, with no built-in drawing behaviour.
rasterize
To decide which pixels a shape covers. For a one-pixel dot there is nothing to decide.
atomic
An operation that completes as one step, so parallel threads cannot corrupt each other's work.
HDR
High dynamic range: pixel values that are real totals and are not capped at "white".
tone mapping
The curve that turns those totals into the 0 to 255 a screen can show.
hash
A function that scrambles a number into a random-looking one, identically every time.
stateless
Nothing is remembered between frames. Everything is recomputed from id, seed and time.
VRAM
The graphics card's own memory.
shot noise
The graininess of counting random arrivals. It shrinks as 1 / √count.
